# Bug Report — Equity Analytics Pipeline

Generated by AI code review across 4 batches. Issues triaged and prioritized below.

---

## Fixed (branch: fix/critical-issues)

### F1 — SQL injection in load.py `get_max_date` / `get_min_date`
**File:** `ingestion/load.py`
**Fix:** Added `_validate_table_name()` whitelist with `frozenset` of allowed table names. Applied to both functions before f-string interpolation.
**Why critical:** Table name came from caller-supplied string with no validation. Any caller passing an attacker-controlled value could inject arbitrary SQL.

### F2 — `CAST` failures on yfinance string sentinels in `stg_valuation_metrics.sql`
**File:** `dbt_project/models/staging/stg_valuation_metrics.sql`
**Fix:** Replaced all `cast()` with `try_cast()` for numeric columns (float and bigint). `cast(extracted_at as timestamp_ntz)` left as CAST — timestamp column is pipeline-controlled.
**Why critical:** yfinance returns strings like `'N/A'`, `'Infinity'` for missing fields. Plain `CAST` throws a hard error and fails the entire dbt run.

### F3 — Value sentinel cap too high in `extract_fundamentals.py`
**File:** `ingestion/extract_fundamentals.py` line 220
**Fix:** Changed `abs(value) > 1e18` → `abs(value) > 1e15`.
**Why:** 1e18 = $1 quintillion. No financial metric reaches that. Legitimate ceiling is ~$1 quadrillion (1e15). yfinance occasionally returns large sentinel floats (e.g., `1e308`) for missing data; the old threshold let those through, corrupting downstream aggregations.

### F4 — Circuit breaker missing in `extract_all_fred_series`
**File:** `ingestion/extract_fred.py`
**Fix:** `extract_fred_series` now returns `None` (not empty DataFrame) for network failures (Timeout, ConnectionError). `extract_all_fred_series` counts consecutive `None` returns and aborts after `CIRCUIT_BREAKER_THRESHOLD = 5`.
**Why critical:** Without a circuit breaker, a FRED API outage causes all 175 series to be attempted, wasting minutes, burning API quota, and potentially triggering rate-limit bans.

### F5 — `re.match` vs `re.fullmatch` for ticker validation in `event_study.py`
**File:** `app/components/event_study.py` line 34
**Fix:** Changed `re.match(r'^[A-Z0-9\-]{1,10}$', ticker)` → `re.fullmatch(r'[A-Z0-9\-]{1,10}', ticker)`.
**Why:** `re.match` anchors at the start but not the end (the `$` in the pattern partially compensates, but `re.fullmatch` is unambiguous). The ticker is used directly in a SQL f-string; the regex whitelist is the only injection guard.

## Deferred Critical Issues

### D1 — Hardcoded Airflow credentials in `docker-compose.yml`
**Lines:** 22–23 (`POSTGRES_USER: airflow`, `POSTGRES_PASSWORD: airflow`)
**Risk:** Credentials visible in source code. Anyone with repo access can connect to the Airflow metadata database.

| | Detail |
|---|---|
| **Pros of leaving** | App is local-only; no external network access to Postgres port. Airflow metadata DB holds only pipeline state, not financial data. Default Airflow credentials are universally known so this is low marginal risk locally. |
| **Cons of leaving** | Becomes a blocker the moment the repo is shared or the stack is deployed to any cloud environment. Bad habit that tends to stay — secrets in code are hard to rotate. If the repo is made public (e.g., portfolio), credentials are immediately exposed. |
| **Fix when:** Before pushing docker-compose.yml to a public repo or deploying to cloud. |

---

### D2 — Private key file on filesystem (not in secrets manager)
**File:** `docker-compose.yml` line 25, `app/db/snowflake.py`
**Risk:** `snowflake_private_key.pem` lives on disk and is mounted into the container. Compromise of the host machine exposes the key.

| | Detail |
|---|---|
| **Pros of leaving** | Key file is gitignored. Local-only deployment means no remote attacker can reach the filesystem. RSA key auth is still far better than password auth. |
| **Cons of leaving** | No key rotation mechanism. If the machine is compromised, the key grants full Snowflake access with no expiry. For cloud deployment, must migrate to a secrets manager before launch. |
| **Fix when:** Before Streamlit Community Cloud deployment — store key in Streamlit secrets or cloud secrets manager. |

---

### D3 — Shell command injection risk in `db_health.py` `_docker_status()`
**Lines:** 165–173
**Risk:** `subprocess` call without explicit `shell=False` and without sanitizing the command arguments.

| | Detail |
|---|---|
| **Pros of leaving** | `_docker_status()` only runs in the admin/health-check context, not in any user-facing path. Arguments are hardcoded Docker CLI commands, not user-supplied input. |
| **Cons of leaving** | If the function signature ever evolves to accept configurable container names, the injection surface opens immediately. Subprocess without `shell=False` is a code smell that can be missed in review. |
| **Fix when:** Next time `db_health.py` is refactored. Low urgency given hardcoded args. |

### D4 — Hardcoded schema `EQUITY_ANALYTICS.MARTS` in `snowflake.py`
**Lines:** Multiple queries in `app/db/snowflake.py`
**Risk:** No environment separation — dev/CI queries hit the same prod schema.

| | Detail |
|---|---|
| **Pros of leaving** | Single environment (local dev + one Snowflake account) means hardcoding works today without complexity. CI runs dbt in a separate `CI_<pr>` schema but the app always reads MARTS. |
| **Cons of leaving** | Cannot run the app pointed at a staging schema for testing. Any schema rename requires grep-and-replace across multiple files. For Community Cloud deployment, want the ability to point at a read-only replica. |
| **Fix when:** When adding a staging environment or deploying to Community Cloud. Use `SNOWFLAKE_SCHEMA` env var. |

---

### D5 — Prompt injection / raw SQL leakage in `chat.py`
**Lines:** 36–51 (raw SQL in chat history sent to Claude API), 81–84 (no input validation on prompts)
**Risk:** User-controlled prompt text is sent directly to Claude API without sanitization. SQL from responses is included in subsequent context turns.

| | Detail |
|---|---|
| **Pros of leaving** | App is local-only with a single trusted user. No multi-tenant risk. Prompt injection from a user to themselves has no threat model. |
| **Cons of leaving** | If Community Cloud deployment happens, any visitor can attempt prompt injection to extract schema info or manipulate Claude's behavior. SQL in history also inflates token usage and cost. |
| **Fix when:** Before Community Cloud deployment. Add a system-prompt instruction to ignore injection attempts; strip raw SQL from displayed history. |

---

### D6 — Hardcoded line items in `int_fundamentals_pivoted.sql`
**Batch 2 critical:** CASE statements hardcode yfinance field names. If yfinance renames a field, pivots silently return NULL.
**Risk:** Silent data corruption in `FACT_FUNDAMENTALS` when yfinance changes schema.

| | Detail |
|---|---|
| **Pros of leaving** | yfinance field names have been stable for years. The EAV staging layer captures everything; only the pivot CASE names are hardcoded. Failures surface as NULL columns, not broken pipeline runs. |
| **Cons of leaving** | NULL columns in fact tables are silent — no alert fires. A renamed field like "Total Revenue" → "Revenue" would zero out all revenue-derived metrics without any error. |
| **Fix when:** Add a dbt test asserting that `total_revenue IS NOT NULL` for a known-good ticker like AAPL. That test catches renames immediately. Low-cost mitigation without a refactor. |

---

### D7 — No API key validation in FRED DAG (`dag_fred_catalog.py`)
**Line:** 86
**Risk:** If `FRED_API_KEY` env var is missing, the task fails with an unhelpful `KeyError` rather than a clear message.

| | Detail |
|---|---|
| **Pros of leaving** | The error is not silent — the DAG fails immediately and logs the KeyError. One-time setup issue, not a recurring risk. |
| **Cons of leaving** | Unhelpful error message slows diagnosis. In CI, a missing secret produces a cryptic failure that wastes time. |
| **Fix when:** Add `if not api_key: raise ValueError("FRED_API_KEY not set")` at DAG entry. 2-line fix. |

## Warnings (not addressed — low priority)

- **docker-compose.yml:** Missing container resource limits; non-deterministic pip installs at runtime.
- **snowflake.py:** Connection retry only handles specific error codes; hardcoded TTL values.
- **chat.py:** Chat history sends SQL to Claude API (token waste, not security risk locally).
- **stg_prices.sql:** Epoch conversion lacks bounds checking.
- **extract_fred.py:** Fixed 0.5s rate-limit delay (no jitter, no adaptive backoff). Acceptable for 175 series sequentially.
- **extract_fundamentals.py:** 2s delay between yfinance calls not configurable.
- **Incremental models:** No late-arriving data handling — corrections for T-5 won't be captured.
